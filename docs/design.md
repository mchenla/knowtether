# 设计与优化方向

## 目标

让知识创作任务在开始、接手和交付时得到可执行的提醒，同时把可机械核对的记录留在本地。工具保持轻量，适合短文，也能为长期成果增加工作单。

`0.2.0` 面向 Python 3.10+，仅使用标准库；以同一规则实现对接 Codex 与 Claude Code。适配器输出协议要求的内容，规则报告负责描述发现，不在 Hook 内作人的接受或发布决定。

## 三个事件

| 事件 | 输入与处理 | 设计理由 |
| --- | --- | --- |
| `SessionStart` | 当前项目及会话信息；提供按需应用的说明，检查工作单的会话绑定 | 在正式工作前提示知识创作要求，发现旧会话记录时提醒重新核对委托 |
| `UserPromptSubmit` | 当前请求的轻量匹配 | 让知识类任务得到较具体的提醒，减少无关任务的干扰 |
| `Stop` | `last_assistant_message` 与当前会话绑定的 `work.json` | 在交付时提示明显遗漏，不读取完整历史，也不要求 Agent 自动续跑 |

无工作单时保留短任务提醒与文本检查；有工作单时增加版本和记录检查。工作单启用、绑定是工具状态，人的授权仍来自实际请求。

Hook 默认告警且返回 `0`，不会向主机发出阻断、批准或重写工具的决定。独立的 `check --strict` 可把 warning/error 变成退出码 `1`，供显式选择的 CI 使用。

## 为什么不强制模板

Core-6 是知识成果需要覆盖的功能。一段解释可以同时表达主张、依据和适用范围；一份研究概览可以暂时没有中心论点。强制标题容易让 Agent 学会填空，无法证明读者获得理解或能力。

自动检查因此只报告具体缺项与可疑信号。文本判断使用启发式，输出应交由人结合任务判断。关于语言自然度的提醒也不应发展成禁词表；专业术语是否必要，要看含义、领域习惯和目标读者。

## 配置与安装

Codex 插件可通过仓库市场用两条命令安装，自带代码和 Skill。用户信任 Hooks 后，插件在知识任务中提供条件性提醒，无须逐项目初始化。显式 `.kpdm/config.json` 可按项目停用；读取工作单使用当前事件 `cwd`，不会把插件缓存当作项目。检测到该目录旧版项目注册时，相同事件由原入口处理，减少重复提醒。详见 [Codex 插件说明](codex-plugin.md)。

原 Python CLI 保留以下按项目安装方式：

安装限于显式指定的项目和主机。先提供 `--dry-run` 供查看改动；实际更新合并已有配置，并备份被修改的配置。Codex 使用 `.codex/hooks.json`；Claude Code 使用 `.claude/settings.local.json`，依赖当前协议的 `command` + `args` 直接执行形式。卸载只删除本项目 handler。安装不会授予主机信任，不会自动全局启用 Hook。Codex 用户需在 `/hooks` 审阅并信任当前定义；Claude Code 旧版若不支持 exec form，需要升级。

工作单仅在创作项目内维护。多会话使用不同工作目录；接手时先核对当前范围再 `bind`。`allowed_write_roots` 是可审阅的委托记录，不能当作操作系统沙箱或工具写入防护。

## 已知限制

- **语义理解有限。** 关键词会漏掉含蓄表达，也可能把教学中的错误例句当作当前主张。没有告警不表示内容通过质量验收。
- **来源核对有限。** 检查引用关系和记录字段，不联网核实来源、不逐字比对引文、不验证数据或许可。
- **上下文有限。** 最后一条消息可能没有完整成果，工作单可能过时或填错。工具不会从完整会话推定授权。
- **人和角色不可验证。** `evidence_ref` 是定位记录，不是身份签名。多个 Agent 或同一模型的不同角色不自动成为独立审查者。
- **主机协议可能变化。** fixture 覆盖本项目使用的样例；真实主机的加载、事件触发、提示显示与会话环境仍需端到端验证。
- **运行不是安全隔离。** 本项目不覆盖全部工具、shell、MCP 或动态脚本，不是访问控制、防泄密或发布安全边界。
- **框架仍处候选阶段。** 适配不会改变原规范版本的接受、试用或验证状态。

## 下一步优化

优先收集真实创作任务中的误报和漏报，记录输入、预期提示、实际结果及其对创作者的影响。删除敏感内容后再贡献样例。

可按以下顺序推进：

1. 在各主机真实会话中记录安装、触发、项目路径、跨会话绑定和卸载结果，形成可复现的兼容表。
2. 用中文和英文的短解释、研究概览、文章及报告校准任务匹配，保留无须工作单的轻量入口。
3. 按实际缺陷增加规则测试，区分“字段存在”“支持材料可访问”“材料支持主张”和“读者任务成功”。后面三项需要不同方法，不能互相替代。
4. 为复杂成果加入可选主张与来源工具，保留人的核验结果及失败记录，避免增加无用必填项。
5. 比较提醒前后真实工作中的修订、误报负担和读者任务结果，再决定是否增加语义审阅能力。

任何基于模型的语义审阅都应显式选择，并说明输入会发送到哪里。未经真实数据与独立核验，不给出质量提升或性能收益数字。

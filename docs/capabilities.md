# 协作行为与结果：能力核对

## 0.4.0 的改进

匹配知识请求后，Hook 读取三份规范、按随包清单校验散列，将完整选段与 [11 项协作要求](../policy/collaboration.md) 送入上下文；缺失、校验失败或超限明确降级。Skill 要求先查阅，无阅读包时运行只读 `prepare`。[机制和证据含义](minimum-reading.md)。

现在已明确要求反迎合、有用异议、授权内主动执行、语境忠实、主张与依据相称、适用时 MECE、自然表达与语法自检，以及读者任务、权利隐私、版本纠错与投入控制。实现是规范读取和行为指导，未新增这些问题的语义检测器、语法纠正器或水印工具。既有四类 Stop 规则不变；不能保证消除任何一类语义问题。实际任务的过程和观察见 [验证记录](validation.md)。

## 0.3.1 逐项审计（历史记录）

核对日期：2026-10-17。适用：0.3.0 的运行逻辑及0.3.1的定位/说明更新。0.3.1没有新增语义审阅器，也没有改变 Hook 提示内容或检查规则。

**目前不能保证彻底消除下表中的任一类问题。** 规范要求、给模型的提示、代码能检查的信号和真实验证结果，是不同层面的事。以下是按用户关注点逐项核对；各关注点可能交叉，不视作互斥分类。

## 逐项核对

| 关注点 | 当前规范/提示 | 自动检查 | 可保证的结果 |
| --- | --- | --- | --- |
| 去谄媚/迎合 | KPDM质量约束要求评价跟随标准与资料，不随作者期待；Hook/Skill有对应提醒 | 没有谄媚语义检测器 | 不能保证消除；合成谄媚反例未告警 |
| 去抬杠 | 人机协议要求在委托内主动推进；Skill允许合理质疑，但未把“有根据的异议”和“无关争辩”做成专门规则 | 没有相关性/争辩检测器 | 不能保证消除；反抬杠的明确行为准则与实测不足 |
| 去无条件顺从 | 来源、未知、反例和风险要求约束执行；重大变更返回人判断 | 工作单能检查部分记录，不能检查是否盲从 | 不能保证消除；合法授权内主动推进也不能误判成盲从 |
| 去断章取义 | 要求来源实际支持主张，保留适用范围与替代解释 | 不读取完整对话，不自动逐段比对源文 | 不能保证；删限定词、偷换范围的合成反例未告警 |
| 去随意断言 | 提醒区分事实、推断、假设、未知 | ABSOLUTE_CLAIM仅匹配“研究证明/科学证明…”附近的若干绝对词；另有来源/状态记录检查 | 只能提示所覆盖模式；“对任何人都必定有效”也可能漏检，不能保证事实正确 |
| 枚举符合MECE | 现有适配没有明确的MECE检查要求 | 没有互斥性/穷尽性语义检查 | 不能保证。分类应先定对象、范围和同一划分维度，再查重叠遗漏；举例或开放清单无需假装穷尽 |
| 去AI文风 | 规范与Skill要求自然表达、必要术语、具体例子；规范还讨论固定句式和标点习惯 | LANGUAGE_PATTERN只检查少数套语及集中出现阈值 | 不能保证自然；能报部分套语，不能确认文本由谁生成或被真人理解 |
| 文法/语法 | 理解性要求可以指导人工/AI修订 | 没有语法、拼写或指代检查器，也不自动改文 | 不能保证无语病；目前无语法质量专项评估 |
| 去水印 | 规范中的“语言指纹”指常见模型用词句式，明确不等于技术水印 | 无统计水印、不可见字符、文档元数据检测/清理实现 | 不支持水印移除，也不保证通过任何AI检测器 |

技术文本水印可以是生成采样时嵌入、通过统计检验识别的信号，并非某个套语或标点。参见原始研究 [A Watermark for Large Language Models](https://arxiv.org/abs/2301.10226)。自然改写、语病修订、不可见字符检查和统计水印检测应分开评估，本工具没有实现后两者的检测/清理。

## 这次做了什么检查

- 检查了 [Hook上下文与四类文本规则](../kpdm_hooks/engine.py)、[Stop执行条件](../kpdm_hooks/hooks.py)、[配套Skill](../skills/knowtether/SKILL.md)及随包[质量约束](../framework/kpdm/spec/01%20Foundations/KPDM%20质量约束.md)和[人机协议](../framework/kpdm/spec/02%20Methods%20and%20Protocols/人机协作协议.md)。
- 用 [13条公开合成输入](../examples/behavior-audit.json)调用真实Stop处理器，而不是让模型评价自己。每条都进入知识文本路径，避免把意图识别没命中混作语义检查结果。
- 四条正对照分别命中了 CITATION_PLACEHOLDER、ABSOLUTE_CLAIM、STATUS_LANGUAGE 和 LANGUAGE_PATTERN。另九条演示性问题文本没有告警，说明目前存在明确漏检；其中不可见字符样例只是U+200B，不是模型统计水印。
- 这些是规则覆盖演示，不是代表性语料、检测率或真实协作效果的统计评估。未告警不代表问题不存在。普通回答若没有命中知识匹配、又没有绑定工作单，还可能根本不进入文本检查。

复现：`python scripts/audit_behavior.py`。脚本只运行合成处理器检查，不调用模型、不改用户配置或项目文件。它只断言正对照规则仍工作；不将漏检固定成需要保留的行为。

## 现有证据能支持哪些表述

| 可以据实说明 | 不应宣传成 |
| --- | --- |
| 已在本机真实Codex会话中触发三个Hook | 所有宿主、所有任务都会触发 |
| 按当前规则返回指导和告警 | 模型一定执行所有要求，或自动修正结果 |
| 0.3.0随包提供72份规范资料 | Agent一定会打开和使用全部规范 |
| 自然写作案例中看到来源、限制、练习等表现 | 已证明减少谄媚/提高事实准确率/读者效果 |
| Hook脚本本身不主动联网、不改成文、不批准发布 | 整个Agent不会联网，或具备完整安全/质量控制能力 |

0.3.0的实际写作案例中，Agent成功读取了Skill，但没有打开framework/kpdm下的规范正文。文章约1800汉字，呈现来源、推断与限制等要求；这不能证明读过规范，也没有对照组证明归因。私有会话和原稿不随开源包分发，此处只记录观察摘要。

## 改进的验收方式

先为每个目标定义正例、反例、适用范围与不应干预的例子，再做可复现评估。反抬杠不能变成迎合，反盲从不能变成拒绝执行正常委托；分类检查不能把所有列表强行做成MECE；去AI文风不能变成“隐瞒AI贡献”的承诺。来源核对需要完整材料与主张对应；语法需要专项检查；真实理解和可用性需要目标读者参与。

以上为 0.3.1 时的待办与证据；0.4.0 的新增机制及其局限见本文开头。

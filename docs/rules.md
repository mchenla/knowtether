## 写作前查阅与协作适配

匹配知识请求后，Hook 校验并提供 [必要原文选段](minimum-reading.md)，不是仅提示有规范文件。新增 [协作要求](../policy/collaboration.md) 明确反迎合、有用异议、授权内主动执行、语境忠实、适用时 MECE、自然表达及相关责任；这些是操作适配，尚不具备相应语义检测或结果保证。学科建设方案见 [扩展草案](../framework/kpdm/extensions/人机协作知识创作学.md)。

## 规则怎样进入工具

| 要求 | 适配方式 | 自动检查的限度 | 人仍需完成 |
| --- | --- | --- | --- |
| 读者、问题与用途明确 | 会话提示；工作单 `intent` | 能发现字段缺失，无法判断目的是否有价值 | 选择受众、用途、范围和质量目标 |
| 探索不强迫先有结论 | 提示允许研究问题与暂定主张；`central_idea` 可说明未定 | 不判定研究是否充分 | 选择问题，决定收敛点，保留未解决项 |
| Core-6 功能覆盖 | 条件提示；按文本信号提供改进建议 | 不要求六个标题；信号存在也不证明功能实现 | 检查读者是否理解且能完成预设任务 |
| 事实、推断、建议与未知分开 | 写作提醒；`claims[].type` 和文本告警 | 不识别所有隐含主张，不自动决定类型正确性 | 核实事实、标明推理前提、处理反例与冲突 |
| 主张可追溯 | `claims[].source_ids` 对应 `sources[].id` | 只能检查记录与引用关系；不核实来源内容 | 对照原文逐项核对是否支持该主张 |
| 引用与许可分别处理 | `sources[].locator`、`rights_status`、`verification` | 权利标签是记录，不是法律认定 | 核实使用条件、署名、敏感信息与披露授权 |
| 按风险增加控制 | 提示数据、强因果、高影响建议、权利、依赖与公开发布要求 | 不做完整风险分类，不扫描所有工具调用 | 按触发项补数据、权利、依赖、变更和领域复核记录 |
| 委托范围与当前版本明确 | `input_version`、`artifact_version`、`delegation`、会话绑定 | 绑定不代表当前授权有效，路径记录不构成访问控制 | 核对人的当前请求，实质改变主张或风险时返回人 |
| 状态与证据相符 | 工作单状态检查；文本状态词提示 | 无法验证证明文件是真是假或独立性是否成立 | 对象、范围、判据、支持记录、核验者、版本、限制齐备 |
| 作者接受与发布决定分开 | `human_decision` 和版本化状态记录 | 有记录不表示工具已经批准 | 人接受具体版本，再作独立的发布决定 |
| 表达自然、术语必要 | 写作提示与部分文本启发式 | 不是 AI 文本检测器，也没有禁词列表 | 使用熟悉术语和具体例子，朗读并由读者或编辑检查 |
| 成品信息服务读者 | 提醒保留读者需要的版本、限制与披露 | 无法可靠判断每段信息的读者价值 | 移除内部会话路径、编辑提示和无用工作流信息 |

实际诊断以当前软件输出为准；本表中的人工要求不会因为没有自动诊断而消失。

## 工作单数据约定

`.kpdm/work.json` 的 `schema_version` 为 `1`。八项内容放在 `worksheet` 中，字段表见 [README](../README.md)。当前会话只有在工作单已启用且绑定匹配时参与 Hook 工作单检查。历史工作单不能静默继承到新的会话。

可选记录示意：

```json
{
  "claims": [
    {
      "id": "C-01",
      "text": "需要被核对的具体主张",
      "type": "method",
      "source_ids": ["S-01"]
    }
  ],
  "sources": [
    {
      "id": "S-01",
      "locator": "可定位的文件、章节或 URL",
      "rights_status": "unknown",
      "verification": "尚未核对原文"
    }
  ]
}
```

`unknown` 用于如实记录缺口，不是发布许可。当前适配器只在 `verification` 为 `human-verified` 时视作有人工核验标签；这仍不证明核验真正发生。定义、方法建议、规范选择、经验和外部事实需要不同的核验；为记录填上 URL 不会把某个判断变成外部事实。`fact`、`data`、`quote`、`cause` 类型还需 `support_note`，说明来源的哪一部分支持该主张。

状态记录要求如下，记录中的 `version` 须对应当前 `artifact_version`，并填写 `evidence_ref`：

| `status` | 需要的记录 |
| --- | --- |
| `draft` | 不要求接受或发布记录 |
| `author_accepted` | `author_acceptance` |
| `independently_verified` | `independent_validation` |
| `release_approved` | `author_acceptance`、`independent_validation`、`release_decision` |

软件只检查记录条件，不核实人的身份，也不替记录签名。保留 `draft` 就不会把尚未发生的决定写成事实。

可选公开用途记录放在 `publication`：`usage` 为 `public` 时，`q_target` 至少 `Q3`，`reader_validation` 与顶层 `independent_validation` 都要有当前版本的 `version`、`evidence_ref`。这些字段只表示已登记相关材料；即使 `--strict` 没有诊断，也不表示满足 Q3。

## 公开发布仍需完成的工作

公开知识成果至少采用 Q3，工作单的简化形式不会免除必要检查：

1. 对核心主张、事实、引文和数据逐项核对，确定来源实际支持表述。
2. 核实外部材料的使用权利和隐私、保密条件。
3. 独立完成事实与引用检查，以及独立编辑或真实目标读者任务；AI 模拟读者只能记为模拟。
4. 记录实际失败、修订和限制。生产完成、自检、测试通过、作者接受、独立复核与允许发布分别表述。
5. 由人接受具体成果版本并单独作出发布决定。

工具测试、示例数据和多 Agent 讨论均不能冒充真实读者、领域复核或外部效度。项目可以按需要增加强度，不能通过改状态字段替代实际检查。

## 数字区间提示

0.4.1 新增 `NUMERIC_RANGE_DASH`：对非代码块中数字之间的长破折号/半长破折号给提示，不自动改文。若是中文正文区间，建议使用带空格的短横线。公式、直接引文可能需要保留，提示不能决定其语义；也不覆盖所有标点、单位或语法问题。

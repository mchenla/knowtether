# KPDM 生产控制层

生产控制层实现 [KPDM 三层元模型](../01%20Foundations/KPDM%20%E4%B8%89%E5%B1%82%E5%85%83%E6%A8%A1%E5%9E%8B.md) 的 Core-6，并执行 [KPDM 质量约束](../01%20Foundations/KPDM%20%E8%B4%A8%E9%87%8F%E7%BA%A6%E6%9D%9F.md)。它服务于可靠协作，不是知识创作的第一性内核。控制按任务的风险与依赖启用：单一主旨、低依赖的任务用一张工作单就够；下文的触发条件命中时，才增加对应的记录与检查。

自 0.5.0-rc.2 起，原《开发生命周期与阶段门》并入本文件「阶段门 G0–G7 与阶段内 PDCA」。

## 裁剪原则

控制强度随 Profile、Q 级、风险和协作复杂度变化：

- 单一主旨、低依赖的文章或报告，用一张工作单合并 ContextPack、WorkPacket 和检查记录；
- 教科书加强学习任务、概念递进和迁移测试；
- 工具书加强检索、步骤、错误处理和完成判据；
- 框架加强对象、关系、适用范围、裁剪、治理和跨场景验证；
- 多人或人机协作加强输入版本、角色、核验点和变更影响记录。

真实性、权利、安全、人的最终责任，以及 Q3/Q4 公开产品的人类可理解性硬门，不得因轻量化被删除。任何必填项都应能说明它支持的判断或要控制的风险；说不出的，就不该是必填项。

## 增加控制的触发条件

轻量入口是默认起点。下列情况出现时，增加对应的支持；每项新增记录都应对应一个需要被发现或被处理的实际问题，而不是照抄整套模板。

| 触发情况 | 增加的必要支持 | 要发现或处理的问题 |
|---|---|---|
| 数据、强因果判断或高影响建议 | 逐项来源核对、相应领域的复核、明确未知与风险处置（主张—证据台账、数据引用记录、不确定性登记） | 数字算错、因果说过头、建议超出证据 |
| 权利不明或敏感材料 | 来源与使用条件记录（来源与权利台账）；在问题解决前限制相应使用 | 无权使用、泄露个人或客户信息 |
| 多章节、多成果或多人依赖 | 版本化 ContextPack、明确任务分工的 WorkPacket、权威矩阵、变更影响记录 | 定义在不同地方各说各话、旧上下文产出被当作最新 |
| 核心定义或方法变化 | 记录 Decision、列出受影响成果、重做相关检查 | 改了一处、别处没跟上 |
| 公开发布 | 至少 Q3；完成对应的独立检查与真实读者测试；Release Gate | 未经核验的内容对外流通 |

增加控制不要求把所有表格填满。字段可以引用已有文件；填「不适用」时说明原因。

## 可用化驱动的验证

每个项目必须在实质生产（Produce）前声明至少一个读者任务，例如：

- 理解：能准确复述、解释或区分；
- 判断：能按适用范围和标准选择或裁决；
- 学习：能练习、迁移并解决新问题；
- 行动：能按方法完成任务并判断完成状态；
- 创造：能使用模型生成符合约束的新成果。

Verify 检查实际结果与失败原因。文本完成、文件齐全、作者满意或 AI 自评均不能代替使用结果；AI 模拟的读者反馈不得填入真实读者结果。检查方法见 [质量高度与验收等级](../03%20Quality%20and%20Governance/%E8%B4%A8%E9%87%8F%E9%AB%98%E5%BA%A6%E4%B8%8E%E9%AA%8C%E6%94%B6%E7%AD%89%E7%BA%A7.md)「读者任务验证」。

## 状态主张控制

项目必须把生产状态、质量状态和发布状态分开记录。最小受控词汇：

- 生产状态：`registered`、`drafted`（草稿写完）、`structurally-reviewed`（结构检查通过）、`author-accepted`（作者接受了某个具体版本）；
- 质量与验证状态：`criterion-ready`、`calibrated`、`field-piloted`、`independently-validated`（独立复核通过）；
- 发布状态：`candidate`、`release-approved`（发布批准）、`withdrawn`；
- 限制限定：`self-assessed`、`provisional`、`unverified`。

草稿写完、结构检查通过、作者接受、独立复核和发布批准是五个分别可识别的状态；缺少发布条件时，不得据其中任何一个登记发布通过。下列情况出现时，对应成果或候选版本不得登记为通过：未接受的新核心主张被写为作者立场；事实、引用、真人反馈或批准记录被虚构；公开成果缺少相应 Q3 检查或目标读者不能完成关键任务；人读规范、模板与机器配置对同一核心规则给出冲突指令；记录形式变轻却丢失了必要来源、风险、责任或接受信息；人要求停止或缩小范围后继续扩展，或把预算耗尽写成问题已解决；引用可访问但不支持主张，或资料间的推测关系被当作已核实事实。项目可以扩展词汇，但每个状态必须有进入条件、退出条件、验证主体和证据位置。状态升级属于 Decision 或 Validation，不得由内容文件自行修改完成。派生视图只能继承或降低权威源的状态，不能升级。

## 阶段门 G0–G7 与阶段内 PDCA

阶段门用于需要阶段控制的项目：多章节、多成果、多人依赖，或 Q3 以上的公开成果。轻量入口的任务不要求逐门登记，但公开发布前仍要满足 G5、G6 对应的检查条件。

### 八阶段

| Gate | 阶段 | 关键产物 | 通过标准 |
|---|---|---|---|
| G0 | 立项与定位 | 工作单或项目章程、ContextPack v1 | 问题、受众、范围、价值和不做事项清楚 |
| G1 | 研究与主张 | 主张—证据台账、ClaimGraph、不确定性登记 | 核心主张已分类，来源与未知项可追溯 |
| G2 | 知识架构 | 概念模型、权威矩阵、GoldenCase 设计 | 对象、关系、层级和定义源唯一 |
| G3 | 规范冻结 | 决策台账、术语和方法基线 | 核心冲突关闭；版本与兼容规则明确 |
| G4 | 内容与工具生产 | 已关闭 WorkPacket、章节、图表、模板、工具 | 按已定架构完成，不发生静默漂移 |
| G5 | 验证 | QualitySLO、回归测试、GoldenCase、读者任务结果、PDCA | 正确性、复现性、可用性和适用范围达标 |
| G6 | 出版工程 | 编辑稿、引用、索引、设计稿 | 内容、语言、法律和版式检查通过 |
| G7 | 发布与演进 | ReleaseCandidate、发布包、反馈库、路线图 | 限制披露、反馈入口、版本治理就绪 |

### 关键依赖

G1 没有主张台账，G2 就会变成凭感觉排目录；G2 没有权威矩阵，G4 会在不同章节重复定义；G5 没有预先确定的门槛，验证会退化为作者自我确认。

允许迭代回流，但不得假装跳过阶段门。文章与报告可采用轻量入口，仍必须覆盖 G0、G1、G2、G5、G6 对应的内容，只是合并在一张工作单里记录。

G0 按 [上下文包与工作包协议](%E4%B8%8A%E4%B8%8B%E6%96%87%E5%8C%85%E4%B8%8E%E5%B7%A5%E4%BD%9C%E5%8C%85%E5%8D%8F%E8%AE%AE.md) 选择轻量入口或展开路径，选择 Q0–Q4，并建立来源、权利、数据和人机协作记录。任何外部发布项目未满足进入条件，不得进入 G4 内容生产。G4 的非琐碎任务由 WorkPacket 或工作单的委托范围控制；G5 必须检查不确定性负荷和回归结果。

### 阶段内 PDCA

1. Plan：确定该阶段产物和通过条件；
2. Do：生产；
3. Check：独立校验；
4. Act：固化、限用或返工。

阶段门只有在 Act 关闭后通过。

### 默认权重

| Gate | 权重 |
|---|---:|
| G0 | 5% |
| G1 | 15% |
| G2 | 15% |
| G3 | 10% |
| G4 | 20% |
| G5 | 20% |
| G6 | 10% |
| G7 | 5% |

项目可在 G0 调整权重，但 Do 开始后不得为美化进度修改。

## 执行机制

Explore、Architect、Produce、Verify 四种模式和四类视角见 [人机协作协议](%E4%BA%BA%E6%9C%BA%E5%8D%8F%E4%BD%9C%E5%8D%8F%E8%AE%AE.md)。同一工作包一次只允许一种主模式；重要模式转换与验收改变才修订合同，不对每次句子修改重复登记。
